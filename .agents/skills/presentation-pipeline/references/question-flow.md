# Question and answer flow

## Формат каждого хода

Пиши компактно:

1. `Этап N/4 — название`.
2. `Зафиксировано:` одно-два предложения, только если появился новый ответ или решение.
3. `Вопрос:` один вопрос, который требует ответа пользователя.
4. `Зачем:` короткое объяснение, только если влияние вопроса неочевидно.

Не создавай видимость анкеты из десятков полей. Вопросы выбираются из контекста, а не задаются механически.

## Типы вопросов

- `intake` — недостающий материал, аудитория, задача или ограничение;
- `choice` — развилка, меняющая структуру, стиль или формат;
- `verification` — факт, источник, право или техническая доступность;
- `approval` — утверждение результата этапа;
- `skip-request` — запрос на пропуск;
- `skip-confirmation` — отдельное подтверждение после описания последствий;
- `resume` — продолжить существующую сессию или начать новую.

У каждого вопроса есть стабильный `questionId`, этап, текст, причина и время. Ответ записывается отдельным decision с тем же `questionId`.

## Вопрос о данных

На этапе 1, если тезисы опираются на числа, а таблиц в материалах нет, задай `intake`-вопрос о данных до gate-вопроса утверждения:

`Вопрос: Есть ли таблицы или выгрузки, из которых будем строить графики?`  
`Зачем: тип графика и заголовок-вывод зависят от того, какие числа реально есть.`

Возможные ответы и их запись:

- файлы приложены → `datasets` с путями и SHA-256;
- данные будут позже → `dataStatus: pending` и блокер в `openIssues`;
- нужны демо-данные → отдельное решение `dataStatus: synthetic`; на слайдах будет метка «ДЕМО-ДАННЫЕ».

Не задавай этот вопрос, если в презентации нет количественных тезисов.

## Gate-вопрос

После валидного результата этапа спроси:

`Результат этапа <название> готов со статусом review. Утвердить его, внести изменения или остановиться здесь?`

Если пользователь утверждает, обнови approval артефакта, пересчитай SHA-256, повторно запусти валидатор и только затем поставь этапу `approved`.

## Пропуск

Запрос пропуска и подтверждение — разные решения. Сначала запиши `skip-request`, покажи последствия, затем создай `skip-confirmation`. Статус `skipped` разрешён только после ответа на второй вопрос.

Примеры последствий:

- без Blueprint сборка не может считаться смыслово проверенной;
- без Style Brief визуальное направление придётся взять из готовой DNA или внешнего пакета;
- без Visual DNA сборка остаётся one-off и хуже переносится на будущие материалы;
- без раздела `dataviz` в Visual DNA графики придётся собирать через `dna-adapter.json` с предложенными ролями;
- без Build пользователь получает только плановые и стилевые артефакты.

## Пауза и возврат

При паузе сохрани текущий вопрос. При возврате сначала сообщи найденный этап, проверку хешей и незакрытый вопрос. Не повторяй уже отвеченные вопросы, если исходные артефакты не изменились.
