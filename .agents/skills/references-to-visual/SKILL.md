# References to Visual

Переведи визуальные материалы в ясные правила для конкретной презентации. Анализируй, а не копируй. Отделяй то, что видно, от того, что известно из официальных источников, и от собственных рекомендаций.

## Результат

Выдай `Visual Style Brief` по контракту `visual-style-brief/1.2` и [шаблону](references/style-brief-template.md). Для автоматической передачи следующему этапу создай `visual-style-brief.json` по [JSON Schema](references/visual-style-brief.schema.json). Результат должен быть достаточно конкретным для сборщика презентации, но не называться брендбуком или дизайн-системой без соответствующих источников и объёма работы.

## Входы

Принимай:

- 1–5 ключевых референсов;
- URL и полностраничные скриншоты;
- PDF-презентации и брендбуки;
- реальные клиентские материалы;
- описание задачи, аудитории и формата;
- утверждённый `Presentation Blueprint` для pipeline mode; в standalone mode он необязателен.

В `pipeline` явно укажи режим:

- `pipeline` — стиль создаётся для конкретного Blueprint; обязательны путь, контракт, версия и SHA-256 Blueprint;
- `standalone` — исследуется самостоятельное визуальное направление; такой бриф нельзя молча выдавать за согласованный с содержанием презентации.

Если дан URL, изучи фактическую страницу, когда доступен браузер или веб-инструмент. Один скриншот не показывает адаптивность, motion, hover-состояния и всю типографическую шкалу — пометь эти ограничения.

## Рабочий процесс

### 1. Определи режим

- `own-direction` — пользователь создаёт или уточняет собственный стиль;
- `client-reading` — пользователь считывает существующую клиентскую айдентику;
- `reference-synthesis` — несколько внешних примеров используются как направление.

В клиентском режиме официальный брендбук и исходные материалы имеют приоритет над визуальными догадками.

### 2. Проверь качество источников

Для каждого источника зафиксируй стабильный `sourceId`, происхождение, дату доступа, тип материала и право использования, только если оно проверено. Используй статусы лицензии `verified`, `restricted` или `unknown`; `unknown` не означает разрешение.

- Предпочитай прямые скриншоты реальных страниц наклонённым мокапам.
- Не смешивай конфликтующие стили молча.
- Не извлекай «официальный» шрифт по внешнему сходству.
- Не считай автоматически найденный цвет официальным токеном бренда.
- Не копируй чужие иллюстрации, логотипы и фотографии в выдачу без разрешения.

### 3. Сделай наблюдательный разбор

Сделай анализ воспроизводимым:

1. зафиксируй URL/путь, дату доступа, размер и состояние источника;
2. для сайта по возможности проверь desktop и mobile, а motion — по фактическому поведению;
3. отличай значения из CSS/официальных файлов от цветов и размеров, измеренных по скриншоту;
4. для каждого измерения укажи единицу, диапазон или погрешность;
5. подтверждай название шрифта только официальным файлом, CSS или документацией.

Для каждого референса отдельно опиши:

- композицию и сетку;
- иерархию и плотность информации;
- характер типографики;
- палитру, температуру и роль акцента;
- формы, линии, радиусы и границы;
- изображения и иллюстрации;
- свет, фактуру и глубину;
- ритм и повторяемость;
- motion и интерактив, если они наблюдаются;
- характер: 3–5 конкретных прилагательных без слова «красиво».

Каждое существенное заключение пометь:

- `Observed` — непосредственно видно или измерено;
- `Confirmed` — подтверждено официальным материалом;
- `Inferred` — обоснованное предположение;
- `Proposed` — рекомендация для этой презентации.

### 4. Задай вопросы о намерении

После первичного анализа задай не фиксированное количество «умных» вопросов, а 2–4 вопроса, которые реально меняют решение. Обычно проясни:

- что именно пользователь хочет сохранить: композицию, настроение, типографику, motion или другое;
- насколько буквально следовать референсу;
- что должно остаться узнаваемым для клиента;
- какие ограничения есть у HTML, PPTX, PDF, проектора и корпоративных шрифтов.

Если ответы уже есть в задаче, не спрашивай повторно.

### 5. Синтезируй, не усредняй

При нескольких референсах сначала найди общие закономерности и противоречия. Если источники расходятся, предложи один главный и один поддерживающий референс либо две явные направления на выбор. Не создавай визуальную кашу средним значением всех решений.

### 6. Сформируй правила для презентации

Переведи анализ в решения:

- 3–5 цветов с ролями и статусом точности;
- рекомендуемые или подтверждённые шрифты, плюс безопасные замены;
- принципы заголовков, основного текста и чисел;
- сетка, поля, плотность и композиционные паттерны;
- 3–6 допустимых визуальных приёмов;
- 3–6 запретов;
- рекомендации по motion только для web-формата;
- один короткий `Style Sentence`, пригодный как контекст для другого агента.

Используй измеримые формулировки там, где материал их позволяет. Если точности нет, пиши диапазон или относительное правило.

### 7. Проверь применимость

Приложи три мини-спецификации: титульный экран, содержательный экран и экран с данными или схемой. Не генерируй финальную презентацию без просьбы.

Для каждой спецификации укажи используемые rule ID, ожидаемый визуальный результат и критерий приёмки. Проверь контраст, читаемость, статическую замену motion и применимость в целевых соотношениях сторон.

### 8. Зафиксируй статус и проверь файл

- `draft` — есть существенные пробелы, конфликт направлений или непроверенные обязательные входы;
- `review` — правила и три контрольных экрана готовы, но направление не утверждено владельцем;
- `approved` — заполнен объект `approval`, нет открытых блокеров и обязательные категории правил представлены.

Запусти `scripts/validate_visual_style_brief.py <путь-к-visual-style-brief.json>`. В pipeline mode добавь флаг `--pipeline`, чтобы отсутствие или повреждение Blueprint стало ошибкой.

## Gotchas

- Название стиля не заменяет правил. «Необрутализм» без композиции, палитры и типографики почти бесполезен.
- Извлечённый стиль — интерпретация, а не юридически официальный брендбук.
- Hex из скриншота искажается цветовым профилем, сжатием и оверлеями.
- Dribbble-мокап может быть концептом, который никогда не работал в реальном продукте.
- Motion нельзя честно восстановить по статичному кадру.
- Похожий шрифт не означает тот же шрифт; всегда указывай уверенность и лицензионный риск.

## Финальная проверка

- [ ] Источники перечислены и различимы.
- [ ] Наблюдения отделены от догадок и рекомендаций.
- [ ] При конфликте референсов принято явное решение.
- [ ] Палитра, типографика, композиция, изображения и motion описаны операционно.
- [ ] Есть замены для недоступных шрифтов и форматов.
- [ ] Нет заявления об официальном брендбуке без подтверждения.
- [ ] Правила можно применить минимум к трём типам экранов.
- [ ] У каждого существенного правила есть rule ID, источник и уровень уверенности.
- [ ] Неизвестная лицензия не трактуется как разрешение.
- [ ] Pipeline mode содержит проверяемую ссылку и SHA-256 Blueprint.
- [ ] JSON использует контракт `visual-style-brief/1.2` и проходит валидатор.
- [ ] `approved` подтверждён владельцем, датой и пройденными критериями.
