# Context Plan Skill

Помоги пользователю сначала принять правильные смысловые решения, а уже затем переходить к слайдам. Принимай сырой разговорный материал без требования заранее заполнить бриф.

## Обязательный результат

Заверши работу одним `Presentation Blueprint` по контракту `presentation-blueprint/1.2`, в котором есть:

1. решение, нужна ли презентация;
2. аудитория, ситуация показа и желаемое изменение после просмотра;
3. выбранный формат и причины выбора;
4. центральный тезис;
5. аргументы, доказательства и статус их проверки;
6. драматургический маршрут;
7. последовательность экранов или слайдов;
8. карта визуализации;
9. список недостающих материалов и проверок;
10. стабильные ID для утверждений, источников и экранов;
11. желаемое действие аудитории;
12. статус результата: `draft`, `review` или `approved` и явная запись об утверждении.

Используй структуру из [шаблона результата](references/output-template.md). Для передачи по пайплайну всегда создавай `presentation-blueprint.json` по [схеме Blueprint](references/presentation-blueprint.schema.json). Markdown без JSON допустим только как результат для чтения, но не как машинный вход следующего этапа.

Статусы имеют строгий смысл:

- `draft` — есть существенные пробелы или рабочие гипотезы;
- `review` — структура полна, но решение ещё не утверждено владельцем;
- `approved` — критерии проверки пройдены, `openIssues` не содержат блокеров и заполнен объект `approval` с владельцем и датой.

## Рабочий процесс

### 1. Собери исходный материал

Прими всё, что уже есть: диктовку, транскрипт, документы, ссылки, таблицы, исследования, брендбук, прошлые презентации и ограничения показа.

- Не заставляй пользователя повторять сведения, которые уже есть в материалах.
- Отделяй авторские мысли от внешних фактов.
- Для каждого внешнего факта сохраняй источник или ставь статус `источник не предоставлен`.
- Таблицы и выгрузки с числами, которые пойдут в графики, регистрируй в `datasets`: `datasetId`, путь к CSV рядом с Blueprint, описание, период, `dataStatus` (`actual`, `modelled`, `synthetic`, `pending`) и `sourceIds`. Если пользователь обещает данные позже, ставь `pending`.
- Не очищай разговорную речь слишком рано: сначала найди авторскую позицию и характерные формулировки.

### 2. Проверь, нужна ли презентация

Рекомендуй презентацию, если визуальная последовательность materially улучшает понимание, убеждение или запоминание. Проверь четыре альтернативы:

- личное объяснение без экрана;
- живая демонстрация продукта или процесса;
- текстовый документ;
- короткое сообщение или письмо.

Если одна альтернатива решает задачу лучше, скажи об этом прямо. При пограничном случае предложи гибрид: короткий рассказ + демонстрация + несколько опорных экранов.

### 3. Выбери формат

Используй такие значения по умолчанию:

- `web presentation` — когда нужны анимация, интерактив, адаптивность, калькулятор, встроенное демо или единая ссылка;
- `PPTX / Google Slides` — когда материал должен редактировать клиент или команда, нужен корпоративный шаблон либо офлайн-показ;
- `PDF` — когда нужна неизменяемая версия для чтения или передачи;
- `live demo + support slides` — когда продукт убедительнее показать, чем описывать;
- `document` — когда материал нелинейный, подробный и предназначен прежде всего для чтения.

Не называй всякую веб-презентацию лендингом. Лендинг предполагает самостоятельную публичную страницу и конверсионный сценарий; линейная презентация в браузере может им не быть.

### 4. Проведи короткое интервью

Сначала извлеки ответы из материалов. Затем задай одним сообщением не более трёх вопросов, только если ответы существенно изменят структуру результата. Если вопрос не блокирует работу, зафиксируй разумную гипотезу и продолжай.

Обязательно проясни:

- кто принимает решение или слушает;
- что происходит до и после показа;
- какую одну мысль аудитория должна унести;
- какое действие или решение требуется;
- какие утверждения требуют доказательств;
- сколько времени и в каких условиях будет показ;
- кто будет владеть и редактировать материал после автора.

Если пользователь не знает ответа, предложи рабочую гипотезу и явно пометь её как гипотезу.

### 5. Собери доказательный каркас

Сформулируй центральный тезис одним предложением. Для каждого аргумента создай связку:

`claim ID → утверждение → зачем оно аудитории → доказательство → source ID → уверенность → владелец проверки → место в рассказе`

Не заполняй пробелы вымышленными числами, кейсами или цитатами. Слабое доказательство отмечай как риск, а не маскируй уверенным текстом.

### 6. Построй маршрут

По умолчанию используй:

`контекст → напряжение или проблема → ключевой вывод → доказательства → решение или метод → результат → следующее действие`

Меняй маршрут под задачу. Для отчёта начинай с вывода, для обучения — с проблемы и принципа, для клиентского предложения — с понимания контекста клиента, а не с рассказа об авторе.

Каждый экран должен выполнять одну работу. Если экран не меняет понимание, не даёт доказательство, не помогает навигации и не побуждает к действию, удали или перенеси его в приложение.

### 7. Создай карту визуализации

Для каждого тезиса выбери форму по правилам из [карты визуальных решений](references/visual-decision-guide.md). Не превращай всё в декоративные картинки.

Если форма — диаграмма данных, укажи в `visualizationMap` `chartType` (тип из карты по отношению в тезисе) и `datasetIds`. Не выбирай тип графика по привычке: «из чего сложился рост» — это `waterfall`, а не два столбца; «факт против цели» — `bullet`, а не спидометр. Числа в `mainPoint` такого экрана должны считаться из зарегистрированной таблицы.

В конце проверь разнообразие: длинная серия одинаковых текстовых слайдов обычно означает, что смысловая работа не закончена.

### 8. Согласуй, затем сохрани

Если решение зависит от выбора пользователя, сначала покажи короткую версию Blueprint. Если входов достаточно или пользователь сразу запросил финальный результат, выдай полную версию без обязательного дополнительного согласования и явно перечисли допущения. Если среда позволяет создавать файлы, сохрани `presentation-blueprint.md`; для автоматической обработки обязательно создай `presentation-blueprint.json`. Затем запусти `scripts/validate_presentation_blueprint.py <путь-к-presentation-blueprint.json>`. Не начинай дизайн без явной просьбы.

## Gotchas

- Не начинай с количества слайдов: сначала определи работу презентации.
- Не путай тему с тезисом. «Рынок AI» — тема; «AI снижает стоимость проверки гипотез» — тезис.
- Не делай вид, что ссылка автоматически подтверждает утверждение: проверь, что источник действительно его поддерживает.
- Не называй непроверенный клиентский стиль официальной айдентикой.
- Не обещай перенос HTML-анимации в PPTX или PDF без тестового экспорта.
- Не придумывай числа для графика, пока нет таблицы: зарегистрируй её как `pending` и оставь блокер в `openIssues`.
- Не переписывай автора в безличный корпоративный язык; сохраняй его позицию и живые формулировки.

## Финальная проверка

- [ ] Понятно, почему презентация нужна или не нужна.
- [ ] Формат выбран по условиям использования, а не по моде.
- [ ] Центральный тезис можно повторить одним предложением.
- [ ] У каждого существенного утверждения есть источник или пометка о проверке.
- [ ] Маршрут ведёт к конкретному действию или решению.
- [ ] Каждая визуальная форма помогает понять смысл.
- [ ] У каждого графика есть `chartType` по отношению в тезисе и `datasetIds` с зафиксированными таблицами.
- [ ] Неясности и гипотезы явно помечены.
- [ ] ID утверждений, источников и экранов уникальны и связаны между собой.
- [ ] JSON использует контракт `presentation-blueprint/1.2` и проходит автоматический валидатор.
- [ ] `approved` подтверждён владельцем, датой и пройденными критериями.
